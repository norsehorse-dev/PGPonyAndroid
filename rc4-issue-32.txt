@AraafRoyall , found it. Bundle mode was loading every attachment fully into memory the moment you picked it, and building parts of the message in memory again on top of that. Your numbers match that exactly: the crash point depends on the phone's memory limit, not on any one file. File mode has streamed from disk since 4.0.4, which is why it handles large files fine, but bundles never got the same treatment.

They have it now. Attachments are read from disk in small pieces during encryption and are never held in memory whole, whether you pick them in the app or share several files into PGPony at once. Size is no longer a factor in any of the three ways files enter a bundle. I'll release RC6 later today, and your 350 MB test is exactly the retest I would ask for.

Your detail that it also crashed with several files adding up to 150 MB is what pointed at the total in memory rather than any single file. That was the useful clue.

RC6 is up: https://pgpony.app/rc/4.2.0-RC-foss/PGPony-4.2.0-RC6-foss.apk (sha256 and signature alongside). Installs over RC5 in place.

Bundles now stream end to end. Attachments are never held in memory whole, whether picked in the app or shared in from another app, and the result is written to disk rather than built as one giant block. Testing at sizes well past yours turned up two more bugs behind the first one, which is the kind of thing your report tends to do: saving a very large encrypted bundle gave no progress indication, so it was easy to grab the file before it finished writing, and an encrypted .eml over a few MB could not be decrypted at all because the decryptor never stripped the mail envelope on the large-file path. Both fixed. My final test was a 750 MB iso plus a stack of photos through the full loop, encrypt, save, decrypt, everything back intact.

Your 350 MB test is the retest I would ask for, in Bundle mode, and try decrypting your own output too since that second path is new.

One honest note on where the practical limit actually sits. A bundle is PGP/MIME, an encrypted email, and mail servers refuse attachments far below these sizes, usually around 25 to 50 MB. So a giant bundle will encrypt and decrypt fine, and the .asc will travel over anything that carries files, but no mail provider will accept it as a message. That ceiling belongs to email, not the app, which is why I fixed the crash instead of adding a size limit. For single large files, File mode remains the natural path.

Your detail that it also crashed with several files adding up to 150 MB is what pointed at the total in memory rather than any single file. That was the useful clue.

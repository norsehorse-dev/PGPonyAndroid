Thank you for the version screenshot. That is what made this findable. Being on 4.0.4 and still seeing the error ruled out the bug I assumed this was.

This is a second, different bug that produces the same error text.

4.0.4 fixed release builds renaming part of the OpenPGP API contract, so the mail client could not read PGPony's reply. That one showed a mangled class name. Yours shows a real class name in org.openintents.openpgp, and the code is -1, which means something failed on the other side of the call. Different direction, different cause.

The cause is mine, and it runs the opposite way to the last one. When FairEmail opens a message, it also hands PGPony the sender's Autocrypt information. That is sent as an object, not as text. Android does not tell the receiving app where to find the class for such an object unless the app asks, and PGPony was not asking. So PGPony failed while reading FairEmail's request. The error travelled back down the connection, and FairEmail reported it the only way it can, as an error on its own side. That is why it looks like FairEmail's fault. It is not.

OpenKeychain works because it asks for that lookup on the first line of the same call. A plain omission on my side.

This also explains why my own testing missed it. The test message must carry an Autocrypt: header for the client to send that information at all, and mine did not. That is now part of the test.

Three things are fixed. PGPony asks for the class lookup. The Autocrypt information is treated as optional, so a bad one cannot fail your decrypt. And errors now name PGPony instead of appearing as a client-side error.

I am working on a small feature release, 4.1.0. This fix is in it.

One thing would help. If you can run adb logcat while reproducing on 4.0.4, I would like the full line after "unmarshalling:". It is cut off in your screenshot. I want to confirm it names the class I think it does, and that it is attributed to com.pgpony.android rather than to FairEmail. If it names FairEmail, I am wrong about this and would rather know now.

Sorry you hit two of these in a row.

Thanks for testing and for tracking the remaining piece down to FairEmail's background behavior. That part is theirs to fix and it is the right place to raise it.

On your question: no, there is nothing hidden or unsafe about using a v4 key normally. v4 is the long-standing OpenPGP key format, and with a modern algorithm (Ed25519, or RSA at 3072 bits or more) it is secure and interoperable everywhere. The only reason to reach for the newer v6 keys is post-quantum protection for the future, which is a separate choice, not a flaw in v4. Use the v4 key with confidence.

Closing since decryption works on 4.2.0. If anything else turns up, open a new issue.

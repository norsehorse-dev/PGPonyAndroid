RC3 ships this, following the #1 thread. Each private key's detail view now has a Decryption Fallbacks list: off by default, toggle the keys you want, reorder with the arrows. The primary is tried first, then your enabled fallbacks in order, and any failure moves to the next. Below it are the three signing default pickers: post-quantum recipients, classical recipients, and signing without encrypting, each defaulting to the key you are looking at.

One design call to flag: when a recipient set mixes classical and post-quantum keys, the classical picker wins, since the classical recipient is the one who needs the backwards-compatible signature.

Download: https://pgpony.app/rc/4.2.0-RC-foss/PGPony-4.2.0-RC3-foss.apk. Installs over RC2.

If the trial order or the mixed-recipients rule does not match what you had in mind, say so now while it is still an RC.

The error I found in the new backwards compatible signing functionality seems to lie in PGPony, because PGPony should produce exactly the same output in the following two cases:

Case 1:
- PGPony is configured for OpenPGP in Thunderbird with an Ed25519 v4 key
- A message is encrypted, signed and sent to a recipient who has a RSA-4096 v4 key

Case 2:
- PGPony is configured for OpenPGP in Thunderbird with a ML-KEM-1024 v6 key
- PGPony also has an Ed25519 v4 private key available
- All three singing defaults in the key details of the v6 key are set to use the v4 key instead
- A message is encrypted, signed and sent to a recipient who has a RSA-4096 v4 key

Case 1 allows the recipient (who is using OpenKeychain) to decrypt and read the message encrypted for their v4 key and signed with a v4 key, case 2 does not allow them to decrypt and read the message that should be encrypted for their v4 key and signed with a v4 key. In both cases, no v6 keys should be used. If PGPony really encrypts the message using the recipients v4 key and signs it using a v4 key, then I can imagine one additional possible error source that is not accounted for: Thunderbird might not ask PGPony to separately encrypt the message that is sent (and should be decryptable by the recipient) and the message that is saved in the folder for sent emails (and should be decryptable by the sender). It might ask PGPony only a single time to sign and encrypt the message for both. If that is the case, we need an additional option in PGPony to use the keys set as a signing default not only for signing but also for encryption when encryption with the same key requested for signing is requested as well. It would probably best to enable the option by default, which should lead to the following behavior:

- Thunderbird asks PGPony to sign a message using private key 1 and encrypt it so that it is decryptable by anyone who is in possession of either private key 1 or the corresponding private key to the recipient's non-PQC v4 public key.
- PGPony realizes that private key 2 is set as signing default for anything that is asked to be signed by private key 1 but sent to a recipient with a non-PQC key and also that the option to also use the signing default for encryption instead if encryption with private key 1 was requested is enabled.
- PGPony responds with an encrypted message that is signed by private key 2 and decryptable by anyone who is in possession of either private key 2 or the corresponding private key to the recipient's non-PQC v4 public key. It must not be decryptable by private key 1 because that would break the backwards compatibility this option would be intended to provide.

@EmanuelLoos , three things.

First a correction on my last comment here: I credited you with the finding that K-9 accepts v4 keys but rejects v5 and v6 on import. That was bluemle's report on #29, not yours. Sorry to both of you for the mix-up.

Second, your diagnosis of the Thunderbird failure was exactly right. Thunderbird sends one sign-and-encrypt request that covers both the outbound copy and encrypt-to-self, so your own v6 key rides along in the recipient set. The composite PKESK that produces is unreadable for any pre-v6 client, and the whole message fails for the OpenKeychain recipient even though their v4 key was addressed correctly. The fix in the next RC: when a signing substitution is active and your own key is among the recipients, the provider swaps your key out of the recipient set and encrypts to the substitute instead. Your sent-folder copy then decrypts with the v4 key, and the v4 recipient reads the message. I made this unconditional rather than a toggle. A setting here would just be a switch between "works" and "silently breaks for pre-v6 recipients", and nobody should have to discover the second position the way you did.

Third, on binding strict fallback mode to the provider: I looked at it and it cannot work the way it does in-app. The OpenPGP API carries no account or key identity on a decrypt call. The client hands the provider a message, and the provider resolves it by the key IDs in the message itself, across the whole keyring. That is the same model OpenKeychain uses. There is no per-key context to hang a strict setting on, so strict mode stays an in-app behavior. If a future API version adds an account extra on decrypt, I will revisit.

Thanks for working the Thunderbird cases as methodically as you did. The next RC will be up shortly and I would value your re-run of Case 1 and Case 2.

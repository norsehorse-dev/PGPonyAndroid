PGPony 4.0.0 is live on GitHub and should be picked up by F-Droid within the next 48 hours. It includes the ECC+Kyber support you asked for, and since you also brought up the OpenKeychain integration, that made it into the same release. Here's where things stand with both.

On the post-quantum side, 4.0.0 implements ML-KEM-768 + X25519 composite encryption in both wire formats that exist today: the IETF draft format (algorithm 35, v6 keys) and the LibrePGP format that GnuPG 2.5.x produces (algorithm 8, v5 keys, the ky768_cv25519 you generated). Your exact repro case now passes end to end. I validated message interop in both directions against GnuPG 2.5.21, so files and messages encrypted by gpg decrypt in PGPony and the other way around. Public key exchange works both ways too, and keys generated in PGPony import cleanly into gpg with the PQC subkey intact. The IETF format implementation is verified against the draft's official test vectors, and everything transfers cleanly between PGPony on Android and iOS.

There are a few limitations you should know about, all on the ecosystem side rather than in PGPony. PQC private keys can't be imported into GnuPG from PGPony or any other app, because gpg stores these secrets in its own internal format and its importer doesn't accept the standard wire form yet. Public keys and messages are unaffected by this. Sequoia's sq preview builds implement an older revision of the IETF draft and can't parse current draft keys, they fail on the draft's own sample key, so no sq interop for IETF format keys until they update. GnuPG itself has no support for the IETF format at all, so keys in that format are PGPony to PGPony for now. And any PQC interop with gpg needs 2.5 or later, since 2.4.x has no ML-KEM support. These are all blocked on the other tools right now, but I'll be watching gpg and sq releases and will get each of these working in later PGPony releases as it becomes possible. Classical keys, RSA and Ed25519, v4 and v6, are completely unaffected by all of this.

On the OpenKeychain replacement, 4.0.0 ships a provider service implementing the same OpenPGP API interface and versions that OpenKeychain 6.0.4 exposed, so any app that could use OpenKeychain as its crypto provider can select PGPony instead. Thunderbird for Android, K-9 Mail, and Password Store are the targets I tested against. Encrypt, decrypt, sign, and verify all work through the API, along with signing key selection, passphrase prompting, streaming for large attachments, and NFC hardware key operations during provider calls. Nothing is allowed by default, each client app gets authorized on first use and pinned to its signature, and you can revoke any of them in Settings under Connected apps. The provider runs on the same crypto core as the rest of the app, so mail encrypted to someone with a post-quantum key works through Thunderbird as well, within the limitations above.

Thanks again for the report and the clean repro steps. If you get a chance to test against your setup once the F-Droid build lands, I'd be glad to hear how it goes.

@monospacedmagic , one more thing while I wait on that certificate: I reproduced the drop directly, standalone against BouncyCastle, outside the app.

A v4-framed subkey carrying an algorithm ID BC doesn't recognize (I tried algo 35, algo 36, and a private-range id) parses the ring without throwing, but the subkey never lands in it. Silent drop, no exception, which matches your screenshot exactly, a ring that reads as a plain v4 Ed25519+Cv25519 pair with no PQC indicator at all.

The root cause is structural, not a bug in how PGPony labels keys. A v5 subkey (the LibrePGP path GnuPG 2.5.x uses for the 768/1024 composites) carries an explicit key-material length, so BC's generic parser can capture unknown-algorithm bytes opaquely and PGPony re-parses that blob afterward. A v4 subkey has no such length at the key level, only the outer packet header knows the total length, so BC has nowhere safe to stop reading an algorithm it doesn't know and drops the packet instead.

What I still don't know is which algorithm ID and framing FreePGP actually emitted. RFC 9980 §3.5 permits ML-KEM-768+X25519 on a v4 encryption subkey, but ML-KEM-1024+X448 is v6-only under the RFC, so if your key is really 1024 on a v4 ring, that's FreePGP doing something the spec doesn't call for. The certificate or gpg --list-packets output would settle it and tell me whether real v4 composite support is worth building.

Good eyes, both of you, and this one deserves a proper explanation because the display is telling the truth.

Every composite key PGPony generates is a hybrid: a classical base (Ed25519 v6 primary for certification and signing, X25519 v6 subkey) with the ML-KEM composite grafted on as an additional encryption subkey. That is true for the 1024 suite too; the X448 half of ML-KEM-1024+X448 lives inside the composite subkey, not in the classical base. So Key Details showing Ed25519, X25519, and ML-KEM for one key is the actual ring layout, not a labeling error.

The part that matters: encryption always addresses the composite subkey. The key selection prefers ML-KEM over the classical X25519 whenever both are present, in the app and in what gets published for others to encrypt to. The classical base exists so the key can still certify, sign, and be understood by software that has never heard of algorithm 36.

@CertainBot on "both Ed and ML as encrypting": if the Ed25519 primary is showing an Encrypt badge on your device, that is a display bug and I want a screenshot. The ML one is correct.

On audits: honest answer, PGPony itself has had no dedicated security audit. The crypto core is BouncyCastle, which is widely reviewed, and the composite implementation is interop-tested against GnuPG in both directions every release, but that is testing, not an audit. The 2015 Cure53 report on OpenKeychain is a good precedent, and a dedicated audit is on the roadmap.

Rebuilt v4.0.3 from a fresh clone with caches cleared, then downloaded the kept
artifact from job 15517255236 and compared all three:

```
your build vs my rebuild:    IDENTICAL (every file)
your build vs published APK: classes.dex, classes2.dex, classes3.dex, baseline.prof
```

So the project is reproducible — Debian/OpenJDK and macOS/Temurin give the same
bytes. The published APK is the outlier.

The difference is 138 bytes in a 17.8 MB `classes.dex`. Same 19,197 classes, same
order; only the source-file attribute differs:

```
r8-map-id-9af7558ea902b208babdac7193a22c8a581831e6435f3540894bc2812bec3e0a   yours + my rebuild
r8-map-id-7180268185d65d6537bcc7452522e7ec9c8d95efca3018b469a5b3cb25ace7ad   published
```

That's R8's map-id — a SHA-256 of the mapping file, embedded in every dex.
`baseline.prof` follows from it, since ART profiles reference dex by checksum.

Root cause: my 4.0.3 release APK wasn't built from a clean checkout of the tag.
Same source, different mapping, different map id. Release builds now come from a
fresh clone, which is what you do and what I should have been doing.

  `446bf9e6…`), which I've verified matches yours exactly, and you re-run; or

I lean towards skipping unless you'd rather get 4.0.3 through, since F-Droid is
on 4.0.0 and 4.0.3 fixes password fields not being marked as password inputs.

builds were renaming the API contract and crashing clients on decrypt), so its
dex will look quite different from 4.0.3.

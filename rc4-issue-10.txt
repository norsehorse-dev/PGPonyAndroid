Thanks, and thanks for attaching the whole design conversation. That changed my answer, because there turned out to be two separate problems and I had only found one of them.

The first is before the decrypt. Every time the decrypt box changes, PGPony works out whether the message is addressed to a hardware key, a software key, or a password. To do that it was loading and parsing every key on your keyring, on the main thread. Each load is an encrypted storage read plus a BouncyCastle parse, so on a keyring of any size that is dozens of round trips before the pasted text can even render. That now runs on a background thread, and it skips the keyring entirely when there is nothing to look up.

The second is the one you are describing, and you were right about it. The decryption itself has run off the main thread since 4.0.4, so that was not the problem. The problem was that the whole decrypted message went into an editable text field. Even read only and capped at fifteen visible lines, Compose still lays out and holds the entire string, along with all the selection and cursor machinery an editable field carries. A long message paid that cost on first display, and paid it again every time the screen scrolled. The fifteen line cap hid how much work was happening, which is why this was not obvious from the outside.

That is now a plain text block instead, which has none of that machinery, and anything past a few thousand characters is held back behind an "Open full text" button. The full body is composed when you ask for it rather than every time you decrypt. You can still select and copy from it either way.

Your structure was the right one, and part of it already existed: a message with attachments already gets a compact result sheet listing them. Plain text never went through it. This brings the two in line.

I am working on a small feature release, 4.1.0. Both fixes are in it.

One question. Which version are you on, and from where? Play is still serving 3.1.0 while the 4.0.x review clears, and 3.1.0 predates the 4.0.4 work that moved decryption off the main thread. If you are on Play, some of this will already be better on 4.0.4 from GitHub or pgpony.app, and knowing that tells me how much of what you saw was the rendering and how much was the decrypt itself.

Test build with both fixes: https://pgpony.app/rc/4.1.0-rc1/PGPony-4.1.0-rc1.apk

SHA-256: ab5a6f08b049b4f00df3a85689038d623a2b12ac8514fa792e42f6862b579771
Detached signature alongside it as PGPony-4.1.0-rc1.apk.asc.

Since you are on 4.0.4 from GitHub, this installs straight over the top. No uninstall, and your keys stay where they are.

It does what you asked in your follow-up: the work happens off the main thread, and the result comes back minimal and expandable rather than as a wall of text. The decrypted message is now a short block with an Open full text button, so the full body is only composed when you ask for it.

On the progress bar, I checked before changing anything, and it is already there for decrypt. Both tabs use the same component, and it shows a byte count with a Cancel button whenever there is a file with a known size. Neither tab shows one for a pasted message, because there is no total to count against and the work should be close to instant. I think what you were seeing was the encrypt side on a file next to the decrypt side on text. If a pasted message still feels slow on this build, that is worth telling me, because it would mean something other than the rendering is wrong.

Your other two suggestions are good but they are separate pieces of work, and I would rather track them properly than bury them in a performance issue.

Volume mounting, DroidFS style. Interesting and quite different from what PGPony does today. The Password Store support is read-only and file-based, so a mounted volume would be new ground. Please open it as its own issue with what you would want it to do.

Multiple methods in one key, as subkeys, like OpenKeychain. PGPony already stores and uses subkeys, so this is mostly about managing them in the UI rather than support existing. There is already work planned around signing subkey selection. Open it separately and I will link it to that.

Let me know how the build behaves.

You were right. The API implementation is fine — the problem was that release builds were renaming the OpenPGP API classes. R8 was obfuscating org.openintents.openpgp.*, and those classes only work between apps if both sides know them by the same name, so clients failed on decrypt. Encrypt kept working, which made it look flaky rather than broken. It affected every client, not just FairEmail.

Fixed and confirmed against a minified release build. 4.0.4 goes out shortly, and the FAQ is being updated alongside it.

Both reproduced and root-caused. Fixes are in 4.0.4.

"Wrong password" before you type anything

When PGPony has been killed, its in-process passphrase cache is empty. The decrypt path went ahead and built the key decryptor with an empty passphrase and let BouncyCastle fail. That failure is a checksum error, indistinguishable from a genuinely wrong passphrase, so the service reported invalid rather than required and the dialog opened pre-flagged.

Fix: check the key's S2K usage before attempting the unlock. A protected key with no passphrase in hand now returns PassphraseRequired, so the prompt opens clean. Unprotected keys are unaffected.

Needing a second Unlock press

The passphrase dialog returned a bare RESULT_OK with no data. Per the API contract, the activity behind RESULT_INTENT has to hand the original request Intent back so the client can re-execute it. Our key-picker activity already did this; the passphrase activity didn't. FairEmail had nothing to retry, so the message only appeared on the second press, which succeeded straight from the now-populated cache.

Fix: the passphrase activity now echoes the original request Intent back on unlock, same contract as the key picker.

Thanks for the detailed report. The second one in particular was only visible from the client side.
